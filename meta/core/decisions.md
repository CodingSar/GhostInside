# Harness decisions

The Backlog decision CLI stores a title only, so the rationale lives here.
`HD-n` is `decision-n` in the harness backlog (`BACKLOG_CWD=meta/core backlog
decision list --plain`). Cite harness decisions as `HD-n`. A bare
`decision-n` always means the product backlog.

| ID | Decision | Why | Rejected | Status |
|---|---|---|---|---|
| HD-1 | Default architecture: vertical slices. | A small model holds one folder in context; a step's allowlist is one folder, so a wrong-file edit is easy to detect. | Layered (controllers/services/repos): every feature touches every layer, so allowlists grow. | amended by HD-11 |
| HD-2 | Default datastore: PostgreSQL only. | One datastore, tested for real, removes a class of mocking and choice errors. | SQLite (diverges from production), document stores (no schema), in-memory fakes. | accepted |
| HD-3 | Stack and test runner undecided until init-factory. | The template serves any product; a premature stack is wrong for most. | A default stack. | amended by HD-5 |
| HD-4 | GhostInside is a template; each product is a user-made `git clone` with the template as the `harness` remote. | Shared history lets harness upgrades merge into products. | GitHub template button (no shared history), a package or submodule (harness files must sit in the repo for Claude Code). | accepted |
| HD-5 | init-factory proposes stack and architecture; the user ratifies at five grouped gates: brief, facets, stack and architecture, packs, provision and seed. | The model researches; the user owns product choices. Grouping keeps the user's effort bounded. | Ask per item (too many prompts); decide silently (no ownership). | amended by HD-15 |
| HD-6 | Defaults HD-1 and HD-2 are priors; a product supersedes them only by a ratified decision. | Defaults fit most products, not all (a CLI with no stored data needs no PostgreSQL). | Hard defaults. | accepted |
| HD-7 | Core guides are template-owned; stack specifics go in overlays. | Core guides stay identical across products, so harness upgrades merge cleanly. | init-factory rewriting core guides. | amended by HD-9 |
| HD-8 | Practices come from the central repo `CodingSar/GhostInsidePractices` as facet packs, vendored with a lock, delta-checked after 7 days; new packs go back by PR and a human merges. | Research is expensive; packs are reused across products and reviewed once. | Research per product; unreviewed writes to the central repo. | accepted |
| HD-9 | Two layers: `meta/core/` is template-owned and never edited in a clone; `meta/product/` is written by init-factory. A product file overrides the core default of the same name (`meta/product/architecture.md` over `meta/core/defaults/architecture.md`). | Defaults and product values in the same files conflict on every harness merge. One rule says who owns a file, and check-harness can enforce it. | Overlays for guides only (HD-7 alone). | accepted |
| HD-10 | The harness backlog lives in `meta/core/backlog/`; the root `backlog/` is the product's and the template ships it empty. | Template tasks in the root backlog shipped into products and collided with product task ids on harness merges. | A task prefix per product (the prefix is read-only after init and template tasks still show up as product work). | accepted |
| HD-11 | Default product architecture: modules (own tables, migrations, `index`) containing use-case slices (`handler`, `rules`, test); `app/` composition root; `shared/` kernel; `_about.md` catalogs; import rules; forbidden catch-all names; size caps. `structure.py` enforces layout, catalogs, names, and caps; the stack's boundary checker enforces imports. | A flat slice list conflated feature, use case, and table owner: a second use case on the same data either bloated one slice or reached around table ownership. Two levels give clear nesting and small allowlists; mechanical caps keep code small without relying on model judgment. | Flat slices (HD-1 as written); layered folders; three or more nesting levels (deeper than a small model needs). | accepted |
| HD-12 | The searcher worker is replaced by `meta/core/tools/packet.py`, which prints the effective architecture, persistence, stack, review rules, and the module and slice files, each line with file and line number. | The packet was nearly the same static files every task; a model copying them "verbatim" could only add error and cost. | Keep the Haiku searcher. | accepted |
| HD-13 | Task lifecycle: the plan lists tests to retire when behaviour changes and the test-writer edits only those; a tidy step runs the check command after green and fixes findings in the plan's files without changing behaviour; test names carry `TASK-n#k`. | No worker could touch an old test, so any behaviour change deadlocked as a deviation. Red-green without refactor let duplication and size grow. `AC1` repeats in every task and stops meaning anything. | Let the implementer edit tests (the spec would drift); a periodic cleanup task (debt piles up between runs). | accepted |
| HD-14 | init-factory holds exactly the five gates of HD-5: provision and seed share one gate, and the skeleton has none because its evidence is command results. The stack rows become one product decision; only superseded defaults and other real choices get their own. | The skill had drifted to seven gates, and one decision per stack row produced about twelve near-identical decisions per product. | Amend HD-5 to seven gates; keep one decision per row. | amended by HD-15 |
| HD-15 | init-factory adds a screens gate between brief and facets, only when the brief's `interface` names a GUI: six gates, five without a GUI. The phase writes static HTML mockups to `meta/product/screens/`, interviews the user on what they expose, and stores the Backlog doc `product-screens`. Seed drafts and orchestrator intake cite screens with `[screen: <id>]`; intake updates a changed screen's mockup and gets confirmation before criteria are final. | Users answer more precisely about a screen than about prose; a mockup surfaces missing states, navigation, and data before facets, stack, and backlog depend on them. A skip rule keeps the cost off CLI, API, and library products. Mockups are throwaway HTML, so workers never build on prototype code. | Text-only brief (gaps surface late, as `ASSUMED:` criteria); a working UI first (needs a stack, which comes later); mockups for every product; a screenshot-versus-mockup verify step now (deferred until a UI stack exists). | accepted |
| HD-16 | The orchestrator is a dispatcher. `meta/core/tools/loop.py` holds the task state machine and runs every deterministic step (preflight, red gate from a JUnit report, tests, allowlist and plan-diff checks, tidy routing, close-out, commits, push). Judgment runs in fresh subagents (intake, planner, test-writer, implementer on Haiku; researcher on a bigger model) that end with one typed `RETURN` line. `call` and `ask` returns push the caller's frame on a stack in `.scratch/<run>/`; the main thread carries out the call or asks the user, and the caller resumes with the result. A Stop hook keeps the main thread on a pending run; a SubagentStop hook rejects replies without a valid `RETURN` line. | Everything runs on Haiku, the main thread included. An orchestrator in context held the procedure, every worker result, and raw test output, more than Haiku keeps straight through a task. Subagents can nest up to three levels (Claude Code docs, 2026-10), but a nested Haiku orchestrator still accumulates context, cannot ask the user, and cannot resume after a cleared context; frames on disk give all three. Deterministic steps in code cannot drift. | Orchestrator in the main thread's context (too large for Haiku); a Haiku orchestrator subagent with native nesting (context grows, no `AskUserQuestion`, no resume); headless launch (banned); an Opus main thread (breaks the Haiku-only rule). | amended by HD-17 |
| HD-17 | The main thread (the orchestrator) runs on Sonnet, set as `model` in `.claude/settings.json` so every clone starts on it. All agents stay on Haiku except the researcher. The dispatcher loop of HD-16 stays. | User decision, 2026-10-10: Haiku pricing rises above 100k context, and a main thread cannot stay under 100k tokens through a task without clearing mid-task. The loop still keeps the main thread small, resumable, and free of procedure drift. | Haiku main thread (HD-16 as written); Opus main thread (cost); dropping the loop now that the main thread is stronger (context and drift come back). | accepted |
| HD-18 | Every agent sets `omitClaudeMd: true` and `effort: medium` in its frontmatter; `check-harness.sh` requires both. | `AGENTS.md` is orchestrator text: Backlog's "run the overview first" and Groma's "run agent-instructions" cost each worker turns and tokens on jobs the guides already specify, and a Haiku worker may follow them. Anthropic's Haiku 5.5 prompting notes (2026-10) report that raising effort from low to medium halved early stopping on multi-step tasks; the agents pin it so the user's session setting cannot lower it. | Keep `CLAUDE.md` for workers (wasted context); session-level effort (drifts with the user's setting); `effort: high` (cost on every worker turn). | accepted |
| HD-19 | Every launch carries its write allowlist in the pending frame (`allow` in `state.json`: exact paths, or prefixes ending in `/`); `guard.py` rejects a subagent Edit, Write, or NotebookEdit outside it and names the list in the reason. The frame prints the list as its last section before the `RETURN` lines. Launches without a list (intake, planner, researcher) keep only the harness protection. The after-the-fact check in `loop.py` stays. | A worker that strayed was caught only after it returned: its whole step was discarded and relaunched, two Haiku runs for one slip. Small models follow negative rules badly (negation scales inversely, arXiv 2209.12711); a deny at the moment of the write, with the allowed paths in the message, is feedback at the point of error, and the list at the end of the frame sits where attention is highest (arXiv 2307.03172). | Prose only ("never edit tests"); the after-the-fact check alone (costs a whole relaunch); a per-agent hook in the frontmatter (one more place to keep in step with `loop.py`). | accepted |
| HD-20 | Workers see test results only as a digest: the verdict and counts, one line per failing test with the first line of its message, or the last 10 output lines when there is no JUnit report, at most 20 lines, plus the log path. `loop.py test "<command>"` is the only way the implementer runs tests; a relaunch after a failed step or red gate restates the job and carries the digest inline. | Raw test output was the largest thing in a worker's context and the one it needed most; the implementer read whole logs, and a relaunch only named a log path. Tests are the best repair feedback when the model sees the failure, not the noise: short greppable lines with the full log in a file (Anthropic, writing tools for agents, 2025; C compiler post, 2026). A retry prompt that restates the goal plus the exact failure beats a pointer. | Raw output in the frame (context rot); the log path alone (one more read, the whole log); a per-stack digest in the overlay (one home per rule: the digest is harness, not stack). | accepted |
| HD-21 | `packet.py --rules` prints the shared rules alone and `--no-rules` leaves them out of a module packet; the loop writes `packets/rules.md` once per run and one module packet per module, and lists the rules first. | A plan over N modules handed each worker N copies of the same rules (about 250 lines each). Repeated coherent text is the strongest distractor measured in context-rot studies (Chroma, 2025), and small models suffer most. Rules once, module content per packet. | One packet per run with everything (a single huge file); rules only in the guide (the guide is template text, the rules are product text). | accepted |
| HD-22 | Every `log.md` line starts with a UTC ISO timestamp; launches log the frame size, relaunches their key, tidy runs their agent. `loop.py report` prints the current run's metrics (task, outcome, elapsed, launches per agent, relaunches, stops, steps green on first try, tidy runs, frame bytes), `--all` one line per run. | The design promised factory-level evaluation (first-pass green, retries, tidy runs, context size) and nothing recorded it. Comparable numbers per run are the prerequisite for any fixture eval (Anthropic, demystifying evals, 2026) and the cheapest signal on whether a harness change helped Haiku. | Metrics in state.json (one more thing to keep consistent); an external tracer (not standard library). | accepted |
